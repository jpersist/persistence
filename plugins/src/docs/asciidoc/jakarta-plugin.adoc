[#jakarta-persistence-plugin]
= Jakarta Persistence Plugin

Plugin ID: `io.github.jpersist.jpa`

The `io.github.jpersist.jpa` plugin is the core implementation of the JPersist plugin suite and facilitates the integration of provider platform plugins such as EclipseLink, Hibernate, and OpenJPA.
It automatically applies the `java` plugin, registers a `persistence` DSL extension, and creates per-source-set tasks for descriptor generation, schema validation, GraalVM native image metadata generation, and static compile-time named query linting.

[#applying-the-plugin-1]
== Applying the Plugin

[source,groovy,indent=0,role="primary",subs="attributes+"]
.Groovy
----
plugins {
    id 'io.github.jpersist.jpa' version '{project-version}'
}
----

[source,kotlin,indent=0,role="secondary",subs="attributes+"]
.Kotlin
----
plugins {
    id("io.github.jpersist.jpa") version "{project-version}"
}
----

[#the-jpa-configuration]
== The `jpa` Configuration

The plugin registers a `jpa` dependency configuration that propagates platform/BOM version constraints into Java compilation (`compileOnly` or `compileOnlyApi` when the `java-library` plugin is also applied) and annotation processing (`annotationProcessor`) configurations.

[source,groovy,indent=0,role="primary"]
.Groovy
----
dependencies {
    jpa platform('org.hibernate.orm:hibernate-platform:6.6.56.Final')

    implementation 'org.hibernate.orm:hibernate-core'
}
----

[source,kotlin,indent=0,role="secondary"]
.Kotlin
----
dependencies {
    jpa(platform("org.hibernate.orm:hibernate-platform:6.6.56.Final"))

    implementation("org.hibernate.orm:hibernate-core")
}
----

[#the-modelgenprocessor-configuration]
=== The `modelgenProcessor` Configuration

The plugin also registers a global, non-resolvable `modelgenProcessor` configuration container that centralizes modelgen annotation processor dependencies. _(Since 1.7.0)_

Each source set's `annotationProcessor` configuration lazily extends from this unified root via `extendsFrom`, so that provider-specific plugins (e.g. Hibernate or EclipseLink) only need to target the single `modelgenProcessor` configuration.
User overrides declared inside `modelgenProcessor` propagate to all source sets and safely skip any built-in defaults added by provider plugins.

[source,groovy,indent=0,role="primary"]
.Groovy
----
dependencies {
    modelgenProcessor 'org.hibernate.orm:hibernate-jpamodelgen:6.6.56.Final'
}
----

[source,kotlin,indent=0,role="secondary"]
.Kotlin
----
dependencies {
    "modelgenProcessor"("org.hibernate.orm:hibernate-jpamodelgen:6.6.56.Final")
}
----

[#dsl-extension-persistence]
== DSL Extension: `persistence`

The `persistence` block is a `NamedDomainObjectContainer` scoped per Java source set.
The plugin automatically creates one entry per source set (e.g. `main`, `test`).

[source,groovy,indent=0,role="primary"]
.Groovy
----
persistence {
    main {
        version = '3.0'

        persistenceUnits {
            'my-unit' {
                provider = 'org.hibernate.jpa.HibernatePersistenceProvider'
                transactionType = 'RESOURCE_LOCAL'

                properties {
                    property 'hibernate.show_sql', 'true'
                }
            }
        }

        validation {
            url = 'jdbc:h2:mem:my_db;DB_CLOSE_DELAY=-1'
        }

        transformer {
            outputProperty 'indent', 'yes'
            outputProperty '{http://xml.apache.org/xslt}indent-amount', '2'
        }
    }
}
----

[source,kotlin,indent=0,role="secondary"]
.Kotlin
----
persistence {
    create("main") {
        version.set("3.0")

        persistenceUnits {
            create("my-unit") {
                provider.set("org.hibernate.jpa.HibernatePersistenceProvider")
                transactionType.set("RESOURCE_LOCAL")

                properties.put("hibernate.show_sql", "true")
            }
        }

        validation {
            url.set("jdbc:h2:mem:my_db;DB_CLOSE_DELAY=-1")
        }

        outputProperties.put("indent", "yes")
        outputProperties.put("{http://xml.apache.org/xslt}indent-amount", "2")
    }
}
----

[#persistenceextension-properties]
=== `PersistenceExtension` Properties

[cols="2,2,2,4"]
|===
| Property | Type | Default | Description

| `version`
| `Property<String>`
| `"3.0"`
| JPA specification version written into the root `<persistence>` element of the generated `persistence.xml`.

| `persistenceUnits`
| `NamedDomainObjectContainer<PersistenceUnitExtension>`
| _auto-populated_
| Named container of persistence unit definitions. Each entry maps to a `<persistence-unit>` element. Units declared in an existing `persistence.xml` template are automatically registered.

| `validation`
| `ValidationExtension`
| _see below_
| Nested database connection configuration for the schema validation task.

| `linter`
| `LinterExtension`
| _see below_
| Nested configuration for the static compile-time `@NamedQuery` analysis linter.

| `outputProperties`
| `MapProperty<String, String>`
| _see below_
| Key-value pairs passed to the XML `Transformer` that formats the output `persistence.xml`.
|===

* `indent` = `yes`
* `omit-xml-declaration` = `no`
* `encoding` = `UTF-8`
* `\{http://xml.apache.org/xslt}indent-amount` = `4`

        transformer {
            outputProperty 'indent', 'yes'
            outputProperty '{http://xml.apache.org/xslt}indent-amount', '2'
        }
    }
}
----

[source,kotlin,indent=0,role="secondary"]
.Kotlin
----
persistence {
    create("main") {
        outputProperties.put("indent", "yes")
        outputProperties.put("{http://xml.apache.org/xslt}indent-amount", "2")
    }
}

| `Property<String>`

                    property 'hibernate.show_sql', 'true'
                    property 'hibernate.format_sql', 'true'
                }
            }
        }
    }

[#multi-tenant-validation]
==== Multi-Tenant Validation

_Since 1.7.0_

The `tenants` container inside the `validation` block allows declaring multiple named database profiles.
When tenants are configured, the `validatePersistenceSchema` task iterates over each tenant and validates every active persistence unit against that tenant's database independently.
Failures are collected across the entire tenant × unit matrix and reported in a single summary.

When no tenants are configured, the base `url`, `driver`, `user`, and `password` properties are wrapped into a single `default` profile automatically, preserving backward compatibility.

[source,groovy,indent=0,role="primary"]
.Groovy
----
persistence {
    main {
        validation {
            tenants {
                primary {
                    url = 'jdbc:h2:mem:primary_db;DB_CLOSE_DELAY=-1'
                }
                secondary {
                    url = 'jdbc:h2:mem:secondary_db;DB_CLOSE_DELAY=-1'
                    driver = 'org.h2.Driver'
                    user = 'sa'
                    password = ''
                }
            }
        }
    }
}
----

[source,kotlin,indent=0,role="secondary"]
.Kotlin
----
persistence {
    create("main") {
        validation {
            tenants {
                create("primary") {
                    url.set("jdbc:h2:mem:primary_db;DB_CLOSE_DELAY=-1")
                }
                create("secondary") {
                    url.set("jdbc:h2:mem:secondary_db;DB_CLOSE_DELAY=-1")
                    driver.set("org.h2.Driver")
                    user.set("sa")
                    password.set("")
                }
            }
        }
    }
}
----

[#legacy-jpa-namespace-support]
== Legacy JPA Namespace Support

_Since 1.5.4_

When the `version` property is set to a legacy JPA specification version (`2.0`, `2.1`, or `2.2`), the plugin automatically switches annotation scanning from the `jakarta.persistence` namespace to the `javax.persistence` namespace.
This ensures correct entity discovery for projects that still target the older Java Persistence API (JPA 2.x), where annotations such as `@javax.persistence.Entity` are used instead of `@jakarta.persistence.Entity`.

The namespace resolution is fully lazy: the version value is read at task execution time via a `flatMap` provider chain, so any DSL overrides applied during the configuration phase are correctly captured.

[cols="1,2"]
|===
| JPA Version | Annotation Namespace

| `2.0`, `2.1`, `2.2`
| `javax.persistence`

| `3.0`, `3.1`, `3.2`
| `jakarta.persistence`
|===

[source,groovy,indent=0,role="primary"]
.Groovy
----
persistence {
    main {
        version = '2.1'

        persistenceUnits {
            'legacy-unit' {
                provider = 'org.hibernate.jpa.HibernatePersistenceProvider'
            }
        }
    }
}
----

[source,kotlin,indent=0,role="secondary"]
.Kotlin
----
persistence {
    create("main") {
        version.set("2.1")

        persistenceUnits {
            create("legacy-unit") {
                provider.set("org.hibernate.jpa.HibernatePersistenceProvider")
            }
        }
    }
}
----

TIP: No additional configuration is needed — the plugin detects the legacy version and adjusts the bytecode scanning annotations automatically.

[#dependency-routing-with-jarfile]
== Dependency Routing with `jarFile`

For multi-module projects, the plugin registers a `jarFile` dependency configuration per source set that allows you to declare module dependencies injected as `<jar-file>` entries in the generated `persistence.xml`.

The `jarFile` configuration extends `implementation` (or `api` when the `java-library` plugin is present).

[#using-the-location-attribute]
=== Using the Location Attribute

[source,groovy,indent=0,role="primary"]
.Groovy
----
dependencies {
    jarFile(project(':common-entities')) {
        attributes {
            attribute(persist.jakarta.gradle.plugin.JakartaPersistencePlugin.JAR_LOCATION_ATTRIBUTE, 'lib/')
        }
    }
}
----

[source,kotlin,indent=0,role="secondary"]
.Kotlin
----
dependencies {
    jarFile(project(":common-entities")) {
        attributes {
            attribute(persist.jakarta.gradle.plugin.JakartaPersistencePlugin.JAR_LOCATION_ATTRIBUTE, "lib/")
        }
    }
}
----

[#using-dsl-jar-file-mappings]
=== Using DSL Jar File Mappings

You can also declare custom jar-file path mappings directly inside a persistence unit:

[source,groovy,indent=0,role="primary"]
.Groovy
----
persistence {
    main {
        persistenceUnits {
            'my-unit' {
                jarFile(project(':ejb-module')) { jarTask ->
                    "${jarTask.archiveBaseName.get()}.jar"
                }
                jarFile 'com.example:external-persistence', 'lib/external-persistence-custom.jar'
            }
        }
    }
}
----

[source,kotlin,indent=0,role="secondary"]
.Kotlin
----
persistence {
    create("main") {
        persistenceUnits {
            register("my-unit") {
                jarFile(project(":ejb-module")) { jarTask ->
                    "${jarTask.archiveBaseName.get()}.jar"
                }
                jarFile("com.example:external-persistence", "lib/external-persistence-custom.jar")

        }
    }

[#tasks-1]
== Tasks

The plugin registers the following tasks per Java source set. For the `main` source set the task names are as shown below; for other source sets (e.g. `test`) the source set name is capitalized and inserted (e.g. `processTestPersistenceDescriptor`).

NOTE: _(Since 1.7.0)_ Per-source-set tasks and configurations are only registered when the source set's `java.srcDirs` or `resources.srcDirs` contain at least one directory that physically exists on disk. Source sets with no on-disk directories are silently skipped, preventing clean IDE workspaces from being cluttered with empty tasks (e.g. `lintTestNamedQueries`).

[#processpersistencedescriptor]
=== `processPersistenceDescriptor`

**Group:** `build` +
**Type:** `ProcessPersistenceDescriptor`

Generates or merges the `persistence.xml` descriptor for the source set.

* **Merge mode:** When a user-provided `src/main/resources/META-INF/persistence.xml` exists, the task parses it, applies extension-defined overrides (provider, data source, properties), injects resolved `<class>` and `<jar-file>` entries, and writes the result to the destination.
* **Generate mode:** When no source descriptor is present, the task builds a complete `persistence.xml` from scratch using the DSL configuration.

The task automatically discovers JPA entity classes annotated with `@Entity`, `@Embeddable`, `@MappedSuperclass`, or `@Converter` using ASM bytecode scanning on the compiled class output.

[cols="2,2,2,4"]
|===
| Property | Type | Default | Description

| `xmlVersion`
| `Property<String>`
| `"3.0"`
| The JPA specification version for the root `<persistence>` element. Bound from `persistence.main.version`.

| `units`
| `ListProperty<PersistenceUnitExtension>`
| _from extension_
| The list of active (enabled) persistence unit configurations to process.

| `includedClasses`
| `ListProperty<String>`
| _auto-discovered_
| Fully qualified class names of discovered JPA entity classes injected as `<class>` elements.

| `jarFileNames`
| `ListProperty<String>`
| _from `jarFile` config_
| Resolved JAR file names injected as `<jar-file>` elements.

| `persistenceXml`
| `RegularFileProperty`
| _optional_
| Path to the user-provided `persistence.xml` template. When present, enables merge mode.

| `destinationFile`
| `RegularFileProperty`
| `build/generated/resources/main/META-INF/persistence.xml`
| The output location of the generated or merged descriptor.

| `transformerSettings`
| `MapProperty<String, String>`
| _from extension_
| XML Transformer output properties controlling indentation, encoding, and formatting.
|===

TIP: The task is automatically skipped when no persistence units are enabled.

[#validatepersistenceschema]
=== `validatePersistenceSchema`

**Group:** `verification` +
**Type:** `ValidatePersistenceSchema`

Validates that the JPA entity mappings align correctly with the database schema by booting an isolated JVM worker process.
Since 1.7.0, validation is performed by an SPI-loaded `SchemaValidator` obtained via `SchemaValidatorFactory`, replacing the previous direct use of the JPA `Persistence` bootstrap API.
The task iterates over every configured tenant profile and validates each active persistence unit against that tenant's database independently.
Failures are collected across the entire tenant × unit matrix and reported in a single summary.

[cols="2,2,2,4"]
|===
| Property | Type | Default | Description

| `jpaVersion`
| `Property<String>`
| `"3.0"`
| The JPA specification version used to determine the annotation namespace (`jakarta.persistence` vs `javax.persistence`) during bytecode scanning.

| `persistenceUnitNames`
| `Property<String>`
| _from extension_
| A comma-separated list of active persistence unit names to validate.

| `validation`
| `Property<ValidationExtension>`
| _from extension_
| Nested database connection configuration (URL, driver, user, password,) and optional multi-tenant `tenants` container.

| `tenantProfiles`
| `ListProperty<String>`
| _from extension_
| Serialized tenant database connection profiles (`Name\|URL\|Driver\|User\|Password`). When no explicit tenants are configured, a single `default` profile is synthesized from the base validation properties. _(Since 1.7.0)_

| `discoveredEntityClasses`
| `ListProperty<String>`
| _auto-discovered_
| Fully qualified entity class names discovered by the ASM bytecode scanner, forwarded to the SPI-loaded `SchemaValidator` for precise mapping resolution. _(Since 1.7.0)_

| `sourceFiles`
| `ConfigurableFileCollection`
| _from source set_
| The Java source files tracked for incremental change detection. Modified sources are mapped to their compiled class counterparts for delta analysis.

| `resourcesDir`
| `DirectoryProperty`
| _from `processResources`_
| The resources directory containing `META-INF/persistence.xml`.

| `validationReportFile`
| `RegularFileProperty`
| `build/reports/persistence/validatePersistenceSchema-report.json`
| The output JSON file containing execution metrics (incremental flag, processed entities, skipped entities) from the validation pass. The report is written under the consolidated `reports/persistence/` directory.

| `classpath`
| `ConfigurableFileCollection`
| _auto-configured_
| The full classpath including compiled entity classes, JPA provider binaries, and the H2 driver.
|===

NOTE: The H2 JDBC driver (`com.h2database:h2:2.2.224`) is transparently injected into the task classpath — no manual dependency declaration is needed.

TIP: The task is automatically skipped when no active persistence unit names are present.

[#generatejpagraalvmmetadata]
=== `generateJPAGraalVMMetadata`

**Group:** `build` +
**Type:** `GenerateJPAGraalVMMetadata`

Generates a GraalVM native image `reflect-config.json` file containing all discovered JPA entity classes to support AOT reflection in native images.

The generated JSON follows the GraalVM reachability metadata format and registers each entity class with `allDeclaredConstructors`, `allDeclaredFields`, and `allDeclaredMethods` set to `true`.

[cols="2,2,2,4"]
|===
| Property | Type | Default | Description

| `sourceFiles`
| `ConfigurableFileCollection`
| _from source set_
| The Java source files tracked for incremental change detection. Monitored incrementally to detect additions, modifications, and removals without relying on compiler output timestamps.

| `includedClasses`
| `ListProperty<String>`
| _auto-discovered_
| Fully qualified class names of discovered JPA entity classes.

| `reflectConfigFile`
| `RegularFileProperty`
| `build/generated/graalvm-resources/main/META-INF/native-image/<group>/<name>/reflect-config.json`
| _(Since 1.8.0)_ The primary output location where the `reflect-config.json` is written. The path follows GraalVM standard conventions using the project group and name.

| `outputFile`
| `RegularFileProperty`
| _convention from `reflectConfigFile`_
| _(Deprecated since 1.8.0)_ Legacy alias for `reflectConfigFile`. Retained for backward compatibility; delegates to `reflectConfigFile` via Gradle conventions. Use `reflectConfigFile` instead — this property will be removed in a future release.
|===

The generated resource directory is automatically added to the source set resources, ensuring the JSON file is indexed by IDEs and packaged into the final JAR.

[#lintnamedqueries]
=== `lintNamedQueries`

_Since 1.6.0_

**Group:** `verification` +
**Type:** `LintNamedQueries`

Performs a static, compile-time AST verification pass over all `@NamedQuery` and `@NamedStoredProcedureQuery` definitions discovered in the compiled source set output.
The task uses ASM bytecode scanning to locate query annotations, then validates JPQL/HQL syntax and parameter naming conventions using an ANTLR4-based parser loaded via SPI.
Processing runs inside an isolated Gradle Worker classloader.

[cols="2,2,2,4"]
|===
| Property | Type | Default | Description

| `jpaVersion`
| `Property<String>`
| `"3.0"`
| The JPA specification version used to determine the annotation namespace (`jakarta.persistence` vs `javax.persistence`) during bytecode scanning.

| `failOnError`
| `Property<Boolean>`
| `true`
| Whether discovering a syntax error or metamodel mismatch immediately fails the build.

| `ignoreWarnings`
| `Property<Boolean>`
| `false`
| Whether sub-critical semantic validation warnings should be muted.

| `sourceFiles`
| `ConfigurableFileCollection`
| _from source set_
| The Java source files tracked for incremental change detection. Modified sources are mapped to their compiled class counterparts for delta analysis.

| `compiledClassesDir`
| `DirectoryProperty`
| _from source set output_
| The directory containing compiled `.class` files to scan.

| `classpath`
| `ConfigurableFileCollection`
| _auto-configured_
| The classpath including compiled classes and the lint persistence libraries.

| `lintReportFile`
| `RegularFileProperty`
| `build/reports/persistence/lintNamedQueries-report.json`
| The output JSON file containing execution metrics (processed files, skipped files, error counts) from the lint analysis pass. The report is written under the consolidated `reports/persistence/` directory.
|===

TIP: The task is automatically skipped when the linter is disabled via `persistence.main.linter.enabled = false`.

[#consolidated-reporting-architecture]
== Consolidated Reporting Architecture

_Since 1.8.0_

All verification and analysis tasks write their output reports under a single `${buildDir}/reports/persistence/` directory tree.
This consolidated layout replaces the previous scattered report locations and makes it easier to locate, aggregate, and publish build reports.

[cols="2,4"]
|===
| Task | Report Path

| `validatePersistenceSchema`
| `build/reports/persistence/validatePersistenceSchema-report.json`

| `lintNamedQueries`
| `build/reports/persistence/lintNamedQueries-report.json`
|===

Provider-specific tasks (EclipseLink, Hibernate, OpenJPA) that produce build artifacts continue to write to their own conventional output directories, while the core JPA verification reports are unified here.
